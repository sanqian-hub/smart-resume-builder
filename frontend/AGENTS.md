## 工作流

- 所有功能开发都从 `docs/requirements/` 下的需求文档开始。
- 开发前先把验收标准拆成测试点，其中组件和逻辑优先用 Vitest，最终用户流程用 Playwright。
- 测试设计时，必须尽量覆盖完整边界条件，而不是只覆盖主流程。
- 改生产代码前，必须先确认至少有一条对应测试处于失败状态。
- 每次只做一个 `red-green-refactor` 循环，不要一次性批量写完所有测试。
- 只实现让当前失败测试通过所需的最小代码。
- 只有在当前测试为绿色后才能重构。
- 未通过 `npm run verify` 前，任务不能视为完成。

## 测试规则

- 只测试用户可以观察到的行为。
- 优先使用 `getByRole`、`getByLabel` 和可见文本，不优先使用脆弱选择器。
- 每条测试只关注一个行为。
- `Vitest` 用于组件、表单状态、校验逻辑和轻量交互。
- `Playwright` 用于路由守卫、跨页面流程和最终集成验收。
- 对于有前端校验的表单，优先覆盖所有已实现的校验分支、空值、长度、非法字符和失败态。
- 在编写或调整 E2E 覆盖前，可使用 `playwright-cli` 做页面探索、截图、问题复现和 DOM 检查。
- 如果流程依赖后端数据，首个 tracer bullet 应优先选择稳定的无登录入口，或显式做桩。

## 交付格式

每个需求默认按下面顺序交付：

1. 说明本次实现对应的需求文档。
2. 列出当前切片覆盖的验收标准。
3. 先新增或修改失败测试，默认优先写 Vitest；只有最终用户流程才写 Playwright。
4. 实现让当前测试通过的最小代码。
5. 在 `test-report.md` 中记录每条关键测试的通过/失败状态、覆盖边界和未覆盖项。
6. 先跑相关测试，再执行 `npm run verify`。
